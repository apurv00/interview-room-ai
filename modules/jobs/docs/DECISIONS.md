# Jobs Feature — Design Decisions & Standing Rulings

**Status:** Living document (v1.0, 2026-07-11). Companion to [INGESTION.md](./INGESTION.md) and [PRODUCT_FLOW.md](./PRODUCT_FLOW.md).
**Provenance:** Seven multi-agent design workflows (2026-07-11), each ending in an adversarial critique pass; every load-bearing claim repo-verified or live-probed. This file is the institutional memory: how we got here, what is settled, what is still the founder's call.

---

## 1. How we got here (the design journey)

1. **Trigger:** Tsenta (YC S26 auto-apply agent) prompted "can we do job discovery on InterviewPrepGuru?"
2. **Strategic verdict:** don't clone auto-apply (crowded, ToS-hostile, off-brand). IPG's unique asset is *demonstrated interview performance*. Differentiator = **the join**: a job list ranked/enriched by longitudinal, evidence-backed readiness, with practicing visibly re-ranking the same job. (Final Round AI ships job matching; MockWin ships JD→mock; **nobody ships the join.** Employer-side validation: Mercor ~$10B, micro1 ~$300M ARR.)
3. **Critical evaluation:** GO-with-changes. Key repo discoveries: paywall is a stub (limits 999999 with an active backfill; enforcement machinery live in `interviewService.ts:150-166` — fires the moment a real cap is set); Inngest not configured in prod; judge model cutover (gpt-5.6-luna) happened 2026-07-10/11 → score-epoch policy + transcript-replay harness needed.
4. **Founder direction #1:** paywall is coming on its own track (approvals pending) — Jobs ships free-first; paywall adds Pro surfaces, never claws back.
5. **Founder direction #2:** Phase 1 cannot assume interview history (readiness bands need ~3 sessions/domain) — cold-start must deliver value day one.
6. **Founder direction #3:** paste-a-JD is already solved by the mock-interview flow — **the product is a personalized feed** ("bring jobs in"). Paste-a-JD demotes to tracker tail.
7. **Founder direction #4:** resume-first personalization ("add your resume to find personalized jobs").
8. **Founder direction #5:** breakdown = (1) job ingestion, (2) product flow (upload resume → build resume → Apply → prep → loop). Both now specced.
9. **Audience measured** (read-only prod aggregates, 2026-07-11): ~76 users, India-heavy, **54% freshers**, **majority non-SWE** (marketing ~20%, sales, business, PM, electrical), profiles nearly empty (2/76 targetRole, 0/76 targetCompanies, 6/76 resumes), 35/76 have practiceStats. This reshaped supply (India-native sources) and onboarding (resume-first, wizard as primary door).

## 2. Standing rulings (settled — do not relitigate)

1. **No auto-apply, ever.** Apply = best-fidelity link-out + tracking + outcome capture. Never price per-application. Also never: cover-letter generation, 50k-page scraping, salary estimation.
2. **Zero hot-path edits.** The 9 hot-path files are never touched. Practice hand-off = `InterviewConfig` (with `jobDescription`) → localStorage → `/lobby` (precedent: `app/(learn)/learn/practice/page.tsx:87-94`; lobby JD-skip verified; generate-question's ~60% JD targeting activates free). Caveat: `InterviewConfigSchema` (validation surface shared with hot-path routes) needs one optional `attribution` field — full accountability process.
3. **Readiness = confidence-banded practice-coverage. Bands, never percentages.** Claims about the user's preparation, never the employer's decision ("employer odds" is banned). The attendance counter says only "Job-specific practice completed: 1/3 sessions"; it is not readiness evidence by itself. "Not ready" is banned copy; Apply is never disabled by a verdict.
4. **Two-vocabulary fit honesty.** Unparsed jobs: "Looks relevant · title & location match." Fit bands only on parsed jobs. Reason chips name the profile field they came from. Never claim re-rank sharpening that didn't happen.
5. **Cost discipline:** JD parse LAZY on first authenticated view (`interview.jd-extract`, ~$0.008, shared across users); the ~35s Sonnet `checkATS` never runs feed-wide or inline (detail-view / background one-shot only); no per-user×job fan-out, ever; rank on-request + cache.
6. **GDPR completeness:** every new user-scoped model lands in BOTH `accountDeletion.ts` cascade and `dataExportService.ts` export + a completeness test (export already had a known gap — `SavedJobDescription`).
7. **Day-1 instrumentation:** `{source:'jobs', jobId, applicationId}` attribution persisted to `InterviewSession` + outcome self-report — the calibration dataset is the only compounding moat and cannot be retrofitted.
8. **Scoring preconditions** for any job-scoped readiness surface: (a) `time_up` taper exemption fix (Phase 1 — today a 15-min session gets tapered + Low-confidence + "ended early" flag, verified in `completionAdjustment.ts`); (b) per-answer→must-have attribution (~2–3d, fast-follow — `SessionSummary` writes only 4 universal dims and drops `jdAlignment`, verified).
9. **Ingestion legal standard:** invited access only (official APIs, robots Allows, advertised sitemaps); never circumvent technical barriers (WAF/robots blocks); link out for apply; never republish JD verbatim; strip recruiter PII at normalize; `revoked` health state honors objections same-day.
10. **Canonical identity guards** (before the first canonical `_id` is minted): never merge same-source/different-`externalId` open postings; exempt `confidentialCompany` from merging; provenance eviction preserves source diversity.
11. **Infra:** Inngest is **already live-synced in prod** (verified 2026-07-11: 8 functions at `/api/inngest`, keep-mongo-warm run history predates today — CLAUDE.md's "not configured" note is stale). Consequence: all crons have been firing; the digest no-oped only because `RESEND_API_KEY` was missing, and the Resend go-live (2026-07-11) made the digest hard-disable PR a same-day deadline. Ingestion has NO inline fallback (no waiting user); Atlas shared tiers all cap at 500 connections (M2 = storage insurance only); sync concurrency ≤2; chunk budgets sized to Vercel Hobby 60s unless the plan check says otherwise.
12. **Metrics honesty:** segment fresher vs professional, never blended averages; `apply_clicked` (machine fact) ≠ `applied` (user claim); kill thresholds set before launch.
13. **Free-first launch posture:** free window = deliberate calibration-data acquisition; paywall (exogenous) adds Pro surfaces (tracked-jobs caps, readiness history), never claws back interviews users have normalized; COGS ceiling watched via feature flag.
14. **Geo scope: India-first supply, geo-agnostic product (founder question, 2026-07-12).** The India weighting is a SUPPLY sequencing decision driven by the measured user base — never a product gate. Non-India users get the full differentiated loop (resume → Fit → readiness → JD-seeded practice → tracker → tailor) with zero geo awareness; only the discovery feed is supply-scoped, degrading to the honest empty state + tracker tail. Consequences: (a) the onboarding location picker accepts ANY location (free entry, not an India-metro dropdown) — uncovered-geo entries ARE the expansion telemetry; (b) expansion to a new country is config, not architecture: a bucket-matrix file + metro aliases + a liquidity-probe run with that country code (JSearch is country-parameterized; the ATS-board layer is US/EU-native and already global); (c) apna/Unstop are India-fresher-segment sources, not templates — each geo gets its own segment-specific sources only if its measured audience needs them; (d) the expansion trigger is tracker-paste + ProductEvent geo demand, the same telemetry-gated adapter policy as everything else.
15. **No flip keys for unsafe behavior (founder ruling, 2026-07-11):** a guard protecting against known-unsafe behavior is a HARD-DISABLE in code, removed only by the PR that fixes the defect — never an env var or flag someone can flip early. Env vars are for credentials and config values (keys, URLs, numeric limits). **[CORRECTED 2026-07-13 — founder]: the earlier carve-out here ("ordinary kill-switch flags remain fine, e.g. jobs_ingest") was the recorder's wording, not the founder's. For the Jobs feature there are NO feature flags at all — behavior switches live in DATA (`JobSourceConfig.enabled`, seeded false; CMS/DB config), and shipped UI is live.** Origin: the email-digest guard on the Inngest enablement PR.
16. **LLM at ingest, rules at serve (founder ruling, 2026-07-12 — supersedes INGESTION §4.5's original "no LLM at ingest" header; full spec in the amended §4.5).** An async, epoch-pinned, enum-coded LLM verdict (`jobs.evaluate-posting`) evaluates every stored posting for genuineness + typed attributes (domain, seniority, fresherFriendly, geo). Invariants: layer-1 deterministic fraud rules stay a permanent BLOCKING floor (per #15 — the LLM only ADDS severity, never the sole fraud gate); verdict is async post-store and never blocks sync (#11); identity never consumes LLM output (#10); serving stays deterministic math over frozen epoch-stamped fields with honest reason-chip vocabulary (#3/#4); every LLM boundary Zod-validated, parse-fail → pending never fabricated; no free-text rationale persisted (#9); modelRouter used additively only (`completion()` is CRITICAL-risk, 405 dependents — the jobs wrapper owns timeout/budget); fraud enforcement = soft-close, never delete; shadow-before-enforce via DB config (per-source/system rows, NOT env flags — founder correction 2026-07-13); probe stays deterministic/byte-untouched with dual-report reconciliation. Rejected in the same ruling: per-user relevancy at ingest (#5 stands), LLM near identity/merging, opaque scalar-driven ranking, salary extraction, embeddings-at-ingest (deferred behind measured Fit failure).
17. **Liquidity is measured at domain × COUNTRY (India + remote), not domain × city (founder ruling, 2026-07-12 — supersedes the city-cell G1 median and <50% bucket-pass rules).** City is a product ranking signal, never a measurement cell or filter. Probe queries stay city-sliced (harvest coverage past the 3-page cap — collection ≠ scoring); the verdict math scores per-domain country-level unique supply (≥20/week + full-JD ≥70% + employer-share ≥30%). Under this scoring, snapshot A (2026-07-11) passes 13/13 domains (109–169 unique fps/domain/week, floors — 21 cells page-capped). City cells remain visible as telemetry. Probe `computeVerdict` amendment lands separately with a `SCHEMA_VERSION` bump persisting per-fingerprint `{tier, fullJd}`; existing artifacts re-score **unique supply** exactly at zero API cost, but their full-JD/employer-share rates are approximate (bucket aggregates double-count cross-city dups, measured 2.5% — inside the gate margins; INGESTION §6 note). G2 freshness and india G6 fresher floors are unchanged by this ruling.

19. **P-3 RESOLVED (founder, 2026-07-14): verdict-chip rule 3 held at launch.** Rules 1/2/4/5 ship; rule 3 ("Worth 2 sessions first") stays dormant behind a DB-config row (JobsVerdictConfig pattern — NEVER an env flag, per the 2026-07-13 no-flags correction) until /cms shows readiness data accruing. Until enabled it degrades to rule 2's copy.

20. **P-4 RESOLVED (founder, 2026-07-14), amended by A06 (2026-07-21): 35-day reversible auto-ghost for confirmed applications only.** The original lazy tracker-GET implementation wrongly treated the machine fact `apply_clicked` as proof of an application and made a read mutate user state. It is superseded. The 7d/21d response nudges and day-35 system transition now apply only to rows with `status:'applied'` and an explicit `appliedAt`; the transition runs in the audited daily `jobs-tracker-status-sweep`, appends `source:'system'` history, and uses status/timestamp CAS plus the account-deletion fence. Tracker GET is physically read-only. `apply_clicked` remains **"Clicked · not confirmed"** until the user confirms or withdraws; it never becomes **"No response"** through inference. `repair:jobs-tracker-status` reverses the narrow historical contradiction while preserving an append-only correction record.

22. **Layered spam defense: link validation is the GENERAL layer; host-blocking is a floor, never the strategy (founder directive, 2026-07-16; broken-link governance amended A09, 2026-07-22).** The hierarchy: (a) **apply-link liveness validation** (hourly machine sweep, `jobs-link-check`) is the only apply-link closure authority and works on any host the spammer moves to. Dead means 404/410, authoritative DNS-nonexistent, all-vetted-address connection refusal, or a 200 page with explicit expiry markers; bot-blocks (403/406/429/999), 5xx, and timeouts remain UNVERIFIABLE. Closing still requires two dead sweeps ≥20h apart and every current apply URL dead. A later authoritative alive observation reverses any crowd or one-check machine soft-ordering and clears the current report window; it never leaves a once-suspect option permanently sunk. (b) **Crowd reports are advisory only.** A report qualifies for the current seven-day incident window only after the same authenticated user has a server-recorded `POST /open?intent=apply` resolution attempt for the same current option/incident within the preceding 24 hours. Three distinct qualifying users reporting in that incident soft-demote the option's ordering; no crowd count hides an option or closes a posting. Seven days bounds report accumulation, not a background wall-clock UI TTL: an expired incident is cleared transactionally by the next trusted Apply open, or earlier by an authoritative machine-alive result. `GET /open?intent=view` and the legacy `/apply-click` mutation create no governance proof; `GET /open?intent=apply` and `POST /open?intent=view` fail closed before application state is touched. The Apply POST is still forgeable by a signed-in caller and the server cannot prove the external page loaded, which is why the consequence remains soft. Legacy reports are soft-only compatibility/audit metadata: old `brokenReportCount` and unbound rows are not current option-demotion authority and can never satisfy the new quorum or become closure evidence. The `3 users / 7 days` threshold and 24-hour attempt freshness are code-owned, not CMS-configurable: they are abuse/safety invariants, and changing them requires reviewed code rather than an operator knob that could silently turn hostile reports into product-wide suppression. The report endpoint has its own Redis-backed six-per-hour identity limit; without Redis that defense fails open, so production Redis and abuse telemetry are operational requirements. (c) **LLM verdict** covers content-level fraud (shadow → enforcement per #16). (d) **APPLY_DOMAIN_BLOCKLIST** stays a zero-cost instant floor for observed-abuse hosts only — never speculative or primary. (e) Manual row revocation remains incident triage only; closing rows without a structural layer invites re-upload.

**Dead-link recovery invariant (A09):** reopening a `dead-apply-link` closure requires two authoritative alive observations at least 20 hours apart for the same current link `subject:generation`. Alive observations from alternating URLs never combine; an unverifiable result preserves only that same link's first recovery strike, while positive death, removal, or generation replacement resets it.

21. **City is NEITHER an input NOR a ranking signal in the jobs product (founder directive, 2026-07-16 — supersedes #17's "product ranking signal" clause; #17's measurement rules are untouched).** Evidence that forced this: the typed-city filter was a HARD pool filter (`$or [{locationKeys}, {isRemote}]`) whose free-text input never went through the metro alias table — 'Bangalore' matched zero rows (stored key `bengaluru`), 'Delhi' zero (stored `delhi-ncr`), silently collapsing the feed to the ~354 remote rows. Removed in the same directive: the feed's city param/filter/rank bonus, the /jobs city box, the start-flow city question, `JobsTarget.city`. `isRemote` stays display-only; location strings still render on cards; `locationKeys` remain ingestion/probe telemetry. Same directive's relevance RCA: targetRole now derives a SOFT domain server-side (`roleToJobsDomain`) — domain-first candidate pull + domain-class-first ordering (the 400-newest cross-domain pull had admitted 15 of 125 open pm rows and recency alone outweighed the domain bonus).

23. **Harvest is de-city'd too: JSearch queries are domain × COUNTRY, never domain × metro (founder cost directive, 2026-07-20 — supersedes #17's "probe queries stay city-sliced (harvest coverage past the 3-page cap)" clause; #17's *measurement* math is untouched).** RCA: #21 removed city from the PRODUCT but left the INGESTION harvest matrix (`bucketMatrix.ts`) fanning each of 23 domains across 6 metros (`${d.q} in ${m}`) — 138 of ~158 daily buckets were city-sliced, a ~3.7× JSearch-quota multiplier layered on a call already scoped by `country=in`. This was defensible under the letter of #17/#21 (harvest = collection, explicitly preserved) but was never re-litigated after the product stopped using city, so the spend ran unchecked and the RapidAPI bill climbed. Fix: `buildHarvestBuckets` now emits `${d.id}:in` (query `${d.q} india`) + the existing `${d.id}:remote` — 158 → 43 buckets. Coverage lost with the metro breadth is recovered with DEPTH, not breadth: `MAX_PAGES_PER_BUCKET` 3→4, and country queries carry enough fresh supply that the §4.4 known-rate cutoff paginates them deeper than a thin metro slice ever did (page-cap safe under the real `maxDuration=300s` step budget, not the stale "Hobby 60s" comment). `metros.ts` / `METRO_ALIASES` stay — `locationKey` dedup is ingestion telemetry (#21) and geo expansion (#14) still keys off a per-country metro file. **Open follow-ups:** (a) the optimal page cap is a tuning knob — read the first country-only cycle's `JobIngestCycle.quotaSpent` + per-domain unique supply before raising it further. (b) **Cap-exit deep-backlog (Codex #559 r3):** collapsing 6 metros into one `:in` bucket means a domain-day with more than `MAX_PAGES_PER_BUCKET`×10 (40) fresh postings cap-exits and the tail beyond page 4 is not revisited — buckets have no continuation, and JSearch's `date_posted` is a RELATIVE window so a feed-style page-resume can't pin a stable query across runs (and "don't advance the cursor on cap-exit" only re-fetches the top 40 on a wider window, costing more without reaching page 5+). Measured supply (~≤24/domain/day vs the 40-row cap, #17) keeps this below the cap in steady state, and the rename's cold-fill backlog is already in-corpus from the pre-#23 metro harvest — so no actual supply loss is expected. A `logger.warn` on every bucket cap-exit now makes any REAL occurrence visible; the proper fix (bucket continuation on an absolute-date cursor, or a targeted cap raise for the affected domain) is a fast-follow gated on that signal firing in prod. The liquidity probe (`scripts/jobs-liquidity-probe.mjs`) stays city-sliced by design (it is the build gate and byte-frozen per #17/#16); only the LIVE harvest changed.
