# Jobs Ingestion Layer — Specification of Record

**Status:** Implementation specification of record (A08 control plane, 2026-07-22).
**Scope:** Source acquisition, normalization, canonical identity, storage, scheduling, quality gating, ops. Product flow is specced separately in [PRODUCT_FLOW.md](./PRODUCT_FLOW.md); standing rulings and open decisions in [DECISIONS.md](./DECISIONS.md).
**Provenance:** Produced by a multi-agent design workflow (exhaustive source sweep with ~110 live endpoint probes on 2026-07-11) plus an adversarial critique pass that re-verified every load-bearing claim. Critique amendments are folded in below and marked **[AMENDED]** where they changed the original synthesis.

Two product-flow dependencies are first-class here:
- **Apply-link fidelity per source** (the product's Apply step is a link-out; link quality is an ingestion concern).
- **Stable canonical job identity across sources** (application tracking references canonical `_id`s forever).

## 3. Legal posture (scraping vs data servicing)

Verified 2026-07-11: apna robots = permissive default (only `*.infra.apna.co/` disallowed) + advertised sitemap; Unstop robots = explicit `Allow: /api/public/*` + named AI-crawler allows. Four-layer analysis:

1. **Technical permission (robots):** clean on apna/Unstop provided we crawl politely — honest branded User-Agent with contact URL, ~1×/day cadence, always obey robots. FW fails this layer (WAF); Naukri prohibits (→ NEVER).
2. **Contract (ToS):** UNVERIFIED — apna's reachable terms doc governs consultants (Order-Form contract), not visitors; Unstop's ToS is an SPA that won't render to a crawler. Browsewrap weakly enforceable against a polite public reader, but continuing after explicit objection = real breach exposure. **Pre-launch action: read both ToS in a browser (10 min) + 30-min counsel skim.**
3. **Content use:** full JD stored internally for matching/practice (transformative); public cards show facts + derived attributes and **link out** for full text and apply — never republish JD verbatim. Strip recruiter contact details from JD text at normalize time (postings aren't personal data under DPDP; embedded recruiter phone numbers are).
4. **Business reality:** value exchange runs toward the sources (login-funnel applies mean they capture the candidate; same bargain that makes boards feed Google-for-Jobs, which is what their JSON-LD exists for). Health machine gains a `revoked` state — any objection → adapter dark same-day. Roster survives without either source.

**Convert grey → white:** send apna + Unstop + Internshala the same short partnership email (attribution + direct link-outs driving candidates to them; ask for a blessed feed).

**Consistency standard (the defensibility):** invited access (ATS APIs, robots Allows, advertised sitemaps) = build; technical barriers (WAF, robots blocks) = never circumvent.

### 4.2 Canonical identity + apply-fidelity ranking — **[AMENDED: false-merge fixes are build-blockers]**

Two-tier identity: source identity `(sourceId, externalId)` as provenance rows (`sourceKey` unique multikey index); canonical `fingerprint = sha256(companyKey|titleKey|locationKey)` unique index. Canonical `_id`s are never reused and never hard-deleted while user-referenced.

Key normalization: companyKey strips legal suffixes only (pvt/ltd/llp/inc) — **never** "solutions"/"technologies"/"consulting" (half of India's consultancy namespace); titleKey drops parenthesized junk + stopwords, keeps seniority tokens, sorts tokens; locationKey via metro alias table (gurgaon|gurugram|noida|delhi → delhi-ncr).

Resolution ladder: sourceKey hit → refresh; fingerprint hit → merge; fuzzy tier (companyKey + location overlap + token-set Jaccard ≥ 0.85 on titleTokens, company-scoped only) → merge; else insert.

**Mandatory amendments (must land before the first canonical `_id` is minted — retro-splitting after apply-tracking ships is a data-corruption migration):**
1. **Never merge two open postings sharing `sourceId` with different `externalId`s** — mass recruiters (and Bosch's own 546) hold N simultaneous identical-title reqs per city; salt the fingerprint with refNumber/ordinal.
2. **Exempt `confidentialCompany` rows from fingerprint and fuzzy merging entirely** — degenerate companyKey merges *different employers*. **Index consequence (Codex on #503):** exempt rows store NO `fingerprint`, and a plain unique index permits only one missing-field document — the `{fingerprint}` index must therefore be a **partial unique** (`partialFilterExpression: { fingerprint: { $type: 'string' } }`) so unlimited confidential rows can coexist while real fingerprints stay unique.
3. Evict provenance (cap 8) by `lastSeenAt` **preserving source diversity** — JSearch's rotating `job_id` must not churn out genuine cross-source entries.
4. Order merge ops delete-before-insert (or transaction) — provenance moves can transiently violate the unique sourceKey index mid-`bulkWrite`.

Merge policy: canonical `applyUrl` = highest tier across all provenance options (`direct-ats > employer > aggregator-deep > platform-funnel > aggregator-redirect`), ties by lastSeenAt then source priority (ats-board > jsearch > india-native). All options retained — rot on the winner promotes the next rung. `jdText` = longest full body; salary conflicts >25% midpoint → `flags.salaryConflict` + range union, never an invented midpoint; `postedAt` = earliest non-null.

### 4.3 Storage budget + Mongo indexes — **[AMENDED]**

The earlier ~4.3 KB/doc / ~125 MB estimate is obsolete: live rows may carry both canonical and display-compressed JDs, and no measured `collStats`/`db.stats()` baseline yet proves physical size or index overhead. Treat **25k retained canonical rows** as the serialized operational safety bound, not a storage forecast; active rows, owner-pinned archives, and tombstones all consume it. Record measured logical/data/index sizes before setting a byte-based alert. Active-feed/source sub-caps must leave headroom inside that retained bound and are tuned post-probe. Index budget: `{fingerprint}` **partial unique** (`partialFilterExpression: { fingerprint: { $type: 'string' } }` — confidential rows carry no fingerprint by design; a plain unique index would reject the second one) · `{'provenance.sourceKey'}` unique · **[AMENDED A02]** `{sourceIds}` (durable legal lineage) and `{'provenance.sourceId'}` (board lifecycle + rolling migration) · `{companyKey, status}` · `{domain, locationKeys, status, postedAt:-1}` · **[AMENDED A12]** partial-open discovery indexes `jobs_feed_open_posted {postedAt:-1,_id:-1}`, `jobs_feed_open_domain_posted {domain,postedAt:-1,_id:-1}`, `jobs_feed_open_remote_posted {isRemote,postedAt:-1,_id:-1}` and `jobs_feed_open_title_posted {titleTokens,postedAt:-1,_id:-1}` · `{purgeAt}` TTL · **[AMENDED 2026-07-12]** `{'llmVerdict.status': 1}` partial (`partialFilterExpression: {'llmVerdict.status': 'pending'}`, the sweeper query) · **[AMENDED A09, 2026-07-22]** `{linkCheckRequestedAt:1}` partial (`partialFilterExpression: {linkCheckRequestedAt: {$type:'date'}}`, non-unique, non-sparse, non-hidden, no TTL or collation; generated name `linkCheckRequestedAt_1`) for the bounded crowd-request lane. A12 deliberately uses ordinary Mongo B-tree indexes and bounded aggregation on the Oracle/Coolify self-hosted target; it adds no Atlas Search, Mongo text index, embedding store or external search service. Verdict and link-governance state live inside the posting/provenance documents—neither adds TTL machinery.

Expiry: ATS missing 2 consecutive polls → closed(`board-poll-miss`); JSON-LD `validThrough` past → closed (and never ingested if already past); canonical `lastSeenAt` > 14d stale → closed(`aged-out`) only for feed/aggregator sources. Pure ATS rows keep the two-clean-poll evidence rule. `lastSeenAt` is top-level and updates on every insert/merge, including provider rows without an `externalId`; the daily sweep backfills missing or malformed legacy values from the newest Date-valued detailed provenance timestamp, falling back to a Date-valued `createdAt`, then the sweep time. Ageable lineage accepts either the durable `sourceIds` rail or legacy detailed provenance. Date-only `validThrough` is canonicalized to end-of-day UTC in both classification and storage, and a contributing source may extend the stored deadline. Fresh canonical evidence newer than an older deadline defers deadline closure, but the row still ages out after that evidence becomes stale. Purge = closedAt + 7d via TTL. **[AMENDED 2026-07-20] User-referenced jobs never purge.** The pin is monotonic in close paths, every ownership write removes `purgeAt`, and close writers first remove any TTL before conditionally stamping one against the current `userReferenced:false` state. Normal expiry/delisting archives retain the shared canonical `jdCompressed` (and current hash-bound `parsedJD`) while referenced so the owner can continue preparation; this is the latest canonical retained body, not an immutable per-user save-time snapshot. A future conservative orphan reconciler may reclaim pins only with race-safe cross-collection coordination. **[AMENDED A04 PHASE 1, 2026-07-21]** `closedReason:'llm-verdict'` rows likewise never purge — deleting the fingerprint would let the same scam posting re-ingest as new. The retention sweep strips display/parsed derivatives from every such tombstone but deliberately retains canonical `jdCompressed`, lineage, provenance and `llmVerdict`; URL-only and epoch re-verdicts therefore never evaluate an empty body. Full body removal is deferred until ingestion has a hash-aware rehydration contract for equal/shorter changed bodies. `source-revoked` and unknown policy closures also expose no retained body through serving. Tombstones are outside active-feed eligibility/counts but **inside the 25k retained-corpus bound** and get their own dashboard gauge (§4.6) so scam-tombstone growth is visible.

**Mandatory owner-retention deployment gate (A05):** writer fixes do not heal TTL contradictions already stored. Every environment containing Jobs data must run this sequence before promotion: (1) `npm run repair:jobs-retention` and retain the dry-run counts; (2) `npm run repair:jobs-retention -- --apply`; (3) `npm run check:jobs-retention`, whose read-only non-zero exit blocks promotion if any application-owned posting is unpinned or any pinned posting still has `purgeAt`; (4) deploy and drain the old workers; (5) repeat apply + check once, because an old in-flight writer can reintroduce a contradiction before it drains. Ordinary PR CI cannot honestly execute this data gate without an environment-scoped staging Mongo credential; the deploy pipeline must wire `check:jobs-retention` to a protected staging environment rather than treating a code-only smoke as proof.

**Mandatory lifecycle deployment gate (A04 phase 1):** the model intentionally does not auto-create the destructive TTL index. Drain old writers, then run this ordered sequence in every environment before enabling the daily worker: (1) `npm run repair:jobs-retention` and retain the dry-run counts; (2) `npm run repair:jobs-retention -- --apply`, which clears every historical `purgeAt` before repairing owners; (3) `npm run check:jobs-retention`; (4) `npm run prepare:jobs-retention-index` and require `Rows carrying purgeAt before index activation: 0`; (5) `npm run prepare:jobs-retention-index -- --apply`; (6) `npm run check:jobs-retention-index`; (7) `npm run sweep:jobs-retention` and retain the planned owner/freshness/closure/TTL/capacity counts; (8) `npm run sweep:jobs-retention -- --apply`; (9) `npm run check:jobs-retention-sweep` and require zero pending mutations. Index creation fails closed if any historical `purgeAt` remains; preparation is non-dropping and a key-identical incompatible index also fails for explicit operator repair. The protected staging workflow executes this sequence against the sentinel-verified database. The runtime sweep checks the exact whole-collection, non-unique `{purgeAt:1}, expireAfterSeconds:0` index before any write, so the cron is inert until activation succeeds. Mongo performs deletion asynchronously after `purgeAt`; the worker never calls `deleteMany` and never decrements the admission counter merely for scheduling. The existing serialized source preflight physically reconciles that safe stale-high counter before admitting new rows.

**Mandatory tracker-status deployment gate (A06):** the old tracker GET may already have converted unconfirmed `apply_clicked` rows to system `ghosted`. New code prevents future contradictions but cannot identify and repair old rows merely by being deployed. Before enabling `jobs-tracker-status-sweep`: (1) run `npm run prepare:jobs-tracker-status-index`; (2) run `npm run prepare:jobs-tracker-status-index -- --apply`; (3) require `npm run check:jobs-tracker-status-index` to verify the exact non-dropping partial due-work index; (4) run `npm run repair:jobs-tracker-status` and retain the dry-run count; (5) run `npm run repair:jobs-tracker-status -- --apply`; (6) require `npm run check:jobs-tracker-status` to pass with zero contradictions. The worker itself checks the exact index before scanning and fails without writing if rollout is incomplete. The repair predicate requires that `appliedAt` is not a BSON Date (including missing, null, and malformed legacy values) and an exact latest system history edge `apply_clicked → ghosted`; it appends a system correction instead of erasing audit history. The protected staging promotion workflow enforces the same sequence. Production follows the Jobs rollout runbook.

**Mandatory A09 link-check index gate:** before unpausing `jobs-link-check`, verify in the exact staging or production database that `jobpostings` contains exactly one key-identical `linkCheckRequestedAt_1` index with the A09 shape above. This is a read-only `getIndexes()` check; it must not call `syncIndexes`, `dropIndex`, or `dropIndexes`. A missing index may be created only with the exact non-dropping `createIndex` call in the [Jobs rollout runbook](./SOURCE_CONTROL_RUNBOOK.md#a09-link-check-index-and-observability); a key-identical incompatible index blocks activation for an explicit migration review. Schema declaration or local tests are not deployed-database evidence.

**Legacy closure support policy:** a closed row with no `closedReason` is restricted, never guessed into a normal archive. Age, a now-expired `validThrough`, or a later-missing source cannot prove why the row originally closed and could misclassify a legal/safety removal. The repair therefore does not backfill reasons. Support copy is: “This older or policy-restricted posting keeps your tracked status, but its original content and new job-specific actions are unavailable.” Any future backfill must use contemporaneous, auditable closure evidence—not present-day heuristics.

Amendments: publish the measured `db.stats()` baseline before trusting the 350 MB alert trigger (existing tenants — transcripts, MultimodalAnalysis, ScoreTelemetry — consume an unmeasured share of M0's 512 MB); **M2 ($9/mo) is storage insurance only** — all shared tiers (M0/M2/M5) cap at 500 connections, so the QA connection-exhaustion risk is carried by the concurrency-2 design, not the upgrade; warn operators at 20k retained rows and transactionally stop new canonical admission above the exact 25k retained-row bound.

#### A12 public discovery read contract

Discovery normalizes public search/company/location values before querying. Domain, search, exact normalized company, freshness and `remote=remote` define the hard live pool. Future or malformed provider `postedAt` values are quarantined before ranking and the top-400 window; a missing date remains eligible as undated and sorts last. Location contributes only a normalized `locationKeys` score bonus, and experience contributes only deterministic title-token bonuses for `entry | mid | senior`; neither may remove unknown rows. The former hard city `$or` pool filter remains prohibited, and `isRemote:false` is not exposed as an on-site guarantee.

The first page fixes a creation boundary and recency clock. Every next/previous cursor carries the filter fingerprint, boundary, score/date tuple and `_id` behind a versioned HMAC; it expires after six hours, rejects tampering and cannot be replayed under another query. The creation fence excludes later inserts while allowing normal lifecycle truth—an existing row may close or receive corrected public facts between pages. The aggregation computes the exact live hard-filter total and separately bounds anonymous enumeration to the top 400 ranked cards. `total`, `accessibleTotal`, `resultCap` and `capped` must remain distinct so UI and telemetry never present the accessible window as corpus size.

Both public GET and personalized POST return the same card projection only; neither contains JD text or apply URLs. The POST adds owner-scoped resume role/skills only in its bounded private/no-store body. Both transports share the route-local Redis-backed 30-request/minute hashed network-identity limit. Vercel identity comes from `x-vercel-forwarded-for`; the Cloudflare/Coolify path prefers `cf-connecting-ip`; absent or malformed identity enters one bounded shared bucket. Missing `REDIS_URL` in production or a Redis counter failure returns 503 before Mongo work. Cloudflare/Coolify must still prevent direct-origin traffic, because no application can authenticate a forged proxy header arriving outside its trusted ingress. These controls limit casual corpus enumeration but are not represented as authentication or perfect anti-scraping.

**Dead-link recovery invariant (A09):** reopening a `dead-apply-link` closure requires two authoritative alive observations at least 20 hours apart for the same current link `subject:generation`. **A03 apply-link network boundary (2026-07-21; A08 browser closure and A09 report governance 2026-07-22):** the production liveness worker accepts only credential-free HTTP(S) URLs on default ports, rejects non-global IP literals and any DNS answer set containing a non-global address, and opens each socket through a vetted address while preserving the original Host/SNI/certificate checks. The candidate-facing Apply ladder and its feed badge use the same structural rule, so localhost, special/private IP literals, credentials, and non-default ports never reach the navigation boundary. Redirects are manual, bounded, downgrade-safe, and re-run the complete URL/DNS/pinning policy on every hop; response reads, DNS, redirects, and connections share one deadline and a bounded body budget. Posting authority is rechecked before DNS, after DNS, and before each physical attempt, so a source revoke or provenance replacement discards the observation. Only authoritative NXDOMAIN, all-vetted-address connection refusal, 404/410, or an explicit closed-job page counts as dead evidence; all ambiguous network failures remain unverifiable. Apply submits an authenticated, rate-limited, same-origin `POST /api/jobs/{id}/open?optionId=…&intent=apply` form synchronously to a new tab; View Source remains `GET /api/jobs/{id}/open?optionId=…&intent=view`. Both method/intent pairs accept only the opaque option identity, re-read the open posting from the Mongo primary, resolve the current safe canonical option, bracket resolution with active-account reads, and return private/no-store responses whose errors never echo a destination. The inverse pairs fail closed before application state changes. Only the Apply POST transactionally records the current option generation and `apply_clicked`; its 303 response guarantees the external employer receives GET rather than a replayed POST. View and legacy `/apply-click` do not create report-governance proof. Even an Apply record proves only that the server resolved a redirect for an authenticated caller, not that the external page loaded. Each report requires the same user's matching attempt from the preceding 24 hours, and three distinct qualifying reporters inside one seven-day incident can therefore only soft-demote ordering. Seven days bounds accumulation; the next trusted Apply after expiry transactionally starts a clean incident, while machine-alive may clear it sooner. Historical `brokenReportCount` and unbound rows are soft-only compatibility/audit metadata, not current demotion or closure authority. Machine liveness alone can close under the two-sweep/all-URLs policy, while a later authoritative alive observation reverses both crowd and single-check machine soft-ordering. The fixed freshness/quorum/window policy is code-owned rather than CMS-configurable because it is a suppression-safety invariant. Visible detail tabs revalidate on visibility return and every four minutes, keeping committed revocation invalidation within the five-minute active-tab SLA. An external job-board page that already accepted navigation still cannot be recalled or receive the liveness worker's DNS pin. The standalone, byte-frozen `scripts/jobs-liquidity-probe.mjs rot` command is not wired to this production transport and must run only from an isolated runner with controlled outbound egress; its output is a build-gate artifact, not a production authorization signal.

**A08 provider-egress gate (2026-07-22):** ingestion adapters now use the shared HTTPS-only pinned provider transport rather than platform `fetch`: it resolves once, rejects the complete answer set when any address is private/malformed, pins each Host/SNI/certificate-checked socket to a vetted address, verifies the connected remote, keeps redirects terminal, caps address attempts and response bytes/time, and makes the authority/Redis quota claim before every physical socket. Before any source is enabled, smokes from the deployed staging and production environments must cover DNS-answer change, direct private/mixed answers, redirect-to-private without credential forwarding, timeout/body/address caps, and exact per-run/day/month exhaustion. Unit tests, compiled-in hosts, and the separate link-liveness smoke do not satisfy that operational gate.

**A02 source-authority protocol (2026-07-21; A08 control plane 2026-07-22):** every `jobs/source.sync` event carries both the source's monotonic legal `controlRevision` and independent `operationalRevision`; audited manual runs also carry `operationId`. `jobs/source.validate` requires all four fields and is valid only while the source is paused. A real no-op fence transaction runs before any paid provider fetch; normalized pages then persist in bounded 25-row transactions. Every such transaction locks the corpus-wide `JobSourceControlMeta` before `JobSourceConfig`, increments both ingest fences, validates both exact revisions plus enabled/health, the permanent legal-audit head, and current permanent operational Enable authorization, then admits its actual insert count only if the serialized retained-corpus total remains at or below 25k. Revoke uses the same global-meta→source-config order, increments the legal revision, disables the source, sets `health:'revoked'` **before** bounded corpus scans, upgrades **all** canonical rows carrying that durable source lineage (open, archived, or multi-source) to the restricted `source-revoked` state with no TTL, and appends a permanent `JobSourceControlAudit`. This order gives every batch and revoke a total order: batch-first is counted and closed by revoke; revoke-first makes that and all later batch fences fail. The LLM ToS worker/sweeper always excludes missing/empty/unknown lineage and additionally excludes every opted-out source in the query, so ineligible legacy rows cannot starve its oldest-first window. **Restore is clearance-only**, not reactivation: the separate idempotent audited action increments legal revision, leaves the source `enabled:false` + `health:'quarantined'`, clears cursors for a future cold validation, and reopens no posting. Bootstrap may add only deploy-reviewed missing catalog rows; enabled legacy rows without matching operational authority are adopted by an audited Pause. Any settings change also pauses an active source and invalidates old validation. All such paths require current-revision Validate → explicit Enable. `POST /api/jobs/admin/source-control` remains the narrow legal primitive behind CMS; operational bootstrap/settings/enable/pause/validate/run-now commands use the separately audited CMS command surface. The permanent legal reason is not returned by monitoring reads; enter a non-sensitive case reference, never privileged narrative or personal data.

**Known A02 boundary:** this is serving revocation, not indiscriminate erasure. Mongo primary reads are forced for authority checks. ### 4.5 Quality gate (two-layer: deterministic floor + async LLM verdict) — **[AMENDED 2026-07-12: founder direction supersedes the original "deterministic only — no LLM at ingest" header; see DECISIONS ruling #16]**

**Layer 1 — deterministic rules (BLOCKING, permanent floor; unchanged).**
**Hard drops** (never stored): blocklist-company (CMS-seeded) · blocklist-apply-domain (bit.ly, forms.gle, wa.me, Telegram) · title-walkin · title-spam-shape (phone in title, >3 slash-joined roles, "N openings", CAPS >0.7) · junk-posting (verified live in foundit) · fee-fraud (registration fee / deposit / pay-for-training) · contact-spam · valid-through-expired · mass-repost (Redis `sha1(JD body)` counter, 7d: same body under >3 companyKeys) · no-company. **Layer 2 — async LLM verdict (`jobs.evaluate-posting` slot; gpt-5.6-luna, maxTokens 800, effort `low` — corpus-scaled, deliberately below the "judgment=high" tier policy).** One call per unique posting evaluates: genuineness verdict `{genuine, suspicious, fraud}` + 1–4 reason codes from a frozen enum (fee_fraud, contact_harvest, pii_harvest, mlm_pyramid, training_bait, fake_company, not_a_job, mass_repost_shell, title_body_mismatch, vague_jd, salary_unrealistic, walk_in_funnel, consultancy_funnel, legit_staffing, thin_but_genuine, ok) + scalars genuineness/quality/completeness + typed attributes `domain`, `seniority`, `fresherFriendly`, `geo {locations, workMode}` (geo-agnostic per ruling #14). Binding invariants:

- **Async post-store, never blocks sync** (ruling #11): a dedicated Inngest worker + hourly sweeper evaluate stored survivors. When verdict collection is enabled (DB config row — no env flags, founder correction 2026-07-13), the store step initializes new survivors with `llmVerdict: {status:'pending', attempts:0}` so the steady-state sweeper runs on the §4.3 partial index; the sweeper ADDITIONALLY catches eligible open or normally archived rows with no `llmVerdict` sub-doc at all (pre-flip corpus, missed enqueues, backfill — a bounded ≤25k-doc scan branch, hourly), so no survivor can sit unevaluated indefinitely behind a missed `jobs/verdict.requested` event. Collection disabled = no init, no sweeper, byte-identical. Pending/invalid verdict ≡ rules-only scoring — degradation is always safe.
- **Monotonicity:** the LLM only ADDS severity; it never overrides a layer-1 drop or flag. Safety/legal closures also outrank normal expiry: board/link close writers use current-status/version CAS, and an exact-input fraud verdict that loses to a normal archive atomically upgrades that archive to `llm-verdict` without overriding `source-revoked` or changed inputs. If that upgrade also loses to a benign ownership-pin write, its missing-or-pending normal archive re-enters the hourly verdict sweep until it scores or the content/lifecycle genuinely changes; restricted and unknown closures never enter that recovery rail. Identity merges that may reopen a normal archive likewise use an acknowledged lifecycle/version CAS; a missed predicate forces a fresh read and policy re-evaluation, so a concurrent `source-revoked` or `llm-verdict` close cannot be reversed by a stale ingest document. Disagreement telemetry is scoped to STORED rows — hard-dropped rows are never stored and never reach layer 2, so drop-side disagreement is undefined by design. Two computable signals, counted per source: `llm-flagged-clean-row` (LLM fraud/suspicious on a rules-clean row — the rules-missed-it signal) and `llm-cleared-flagged-row` (LLM ok/legit_staffing on a demotion-flagged row — advisory only; the flag stands). The injection/drift alarm is a per-source anomaly in these rates (rising clean-rate on flagged rows, or falling LLM-added-severity rate).
- **Verdict binds to `verdictInputHash` = sha256(companyKey | titleKey | locationKey | normalizedBody | sorted apply-hosts | salaryPresence | promptVersion | epoch)** — never body-hash alone (provenance merge swaps apply URLs without touching jdText). **[PRECISED 2026-07-14]** `normalizedBody` = the PII-stripped, model-visible head-3000+tail-1500 slice — content beyond the window the model never saw cannot invalidate its verdict, and the PII strip only ever runs on the bounded slice (ReDoS surface otherwise). The merge layer owns invalidation: any JD replacement or apply-URL change on a stored row resets a scored verdict to `pending` (fresh attempts), which is also the §4.3 tombstone re-verdict path. Input change re-enqueues; verdicts are immutable within an epoch (`epoch = actualModel:promptVersion`); epoch cutover = founder-triggered rolling budget-capped re-classification, replay-compared on the golden set (ruling #8 discipline).
- **Prompt hygiene:** one prompt sees all fields together (split-signal scams); `DATA_BOUNDARY_RULE` + instructions outside `<job_posting>` tags; metadata through `neutralizePromptLine`; body = classifyJob-normalized (tag-strip + entity-decode + residual `<>` strip), head 3000 + tail 1500 chars; recruiter-PII strip (ruling #9) strictly precedes any LLM call; per-source verdict opt-out on `JobSourceConfig` (ToS lever). Output = closed enum codes only, Zod-validated; **no free-text rationale persisted**; parse-fail/truncation → `pending`, never fabricated, never `clean`.
- **Enforcement (I-4):** `fraud` + genuineness ≤ 0.2 → **auto soft-close** (`closedReason:'llm-verdict'`, fingerprint intact = anti-resurrection, never deleted, CMS-reviewable/reopenable); `suspicious`/low-quality → stored demotion fields consumed by serving as deterministic math with honest reason-chip vocabulary (rulings #3/#4). Identity (§4.2) never consumes LLM output (ruling #10).
- **Rollout:** DB-config switches, NOT env flags (founder correction 2026-07-13) — verdict collection and enforcement are system config rows (CMS-editable), both defaulting OFF; shadow ≥2 ingest weeks with exit criteria (error <5%, backlog age <24h, spend ±30% of estimate, fraud false-positive rate on the labeled-genuine golden set <2%, founder-reviewed disagreement drill-down).

- **Probe reconciliation:** the liquidity probe stays byte-untouched and deterministic (it is the build gate). `JobIngestCycle` dual-reports per-bucket yield rules-only (probe-comparable) AND rules+LLM (reality); enforcement flips only if G1/G6 still pass on rules+LLM yield.

### 4.6 Observability (<2 hrs/week ops)

`JobIngestCycle` rows have a 30d TTL and a `kind: 'sync' | 'llm-verdict' | 'link-check'` discriminator. Sync rows record fetched/normalized/driftNulls, per-rule drops, new/merged/refreshed/closed, dupCollapsedPct, physical `quotaSpent`, request-stop reason, and health transitions. Verdict rows record `{requested, scored, cacheHits, errors, timeouts, softClosed, verdictDistribution, reasonCodeCounts, bySource, disagreementCount, tokens, costUsd, epoch}` plus per-bucket yield dual-report (rules-only vs rules+LLM). A09 link-check rows record `{checked, dead, alive, unverifiable, closedNow, requestedProcessed, crowdDispositionChanged, machineDispositionChanged, incidentsCleared, casMisses, reopenedNow}`. `checked` counts successful current-lifecycle CAS writes; `dead + alive + unverifiable` must equal it. Disposition and incident counters are per current URL subject/generation and may exceed posting counts. Queue depth and oldest request age are deliberately queried from `jobpostings`, because a cycle row records completed work rather than pretending to snapshot arrivals racing that run.

Run `npm run report:jobs-discovery-quality -- --sample-per-source=5` for the read-only A12 seven-day cohort report. It emits overall and per-domain usable supply, freshness known-rate/median/p90/within-seven-day rate, top-one/top-five employer concentration with explicit exclusions, and the observed JSearch quota-per-retained-usable-job ratio. `JobIngestCycle` has no domain/bucket quota attribution, so the report refuses to invent a per-domain ratio and marks missing cycle quota as a lower bound. Remote precision is not inferred from `isRemote`; the report emits a deterministic source-stratified queue with blank manual labels and calculates no precision until a human audit exists. The output excludes JD bodies and apply URLs.

The hourly link-check operational contract is: alert immediately on a terminal Inngest failure and page when no finished `link-check` cycle exists for two schedule intervals; warn when the oldest eligible `linkCheckRequestedAt` is older than two hours and page at six hours; investigate CAS misses above 10% of (`checked + casMisses`) for two cycles; investigate `unverifiable / checked >= 50%` for two cycles with at least 20 checks; and page on either `closedNow >= 10` or `closedNow / checked >= 10%` in one cycle. Individual demotions, incident clears, and reopens are expected lifecycle signals, not pages; trend them and investigate a coordinated crowd-demotion spike, a machine-demotion spike aligned with unverifiable/dead growth, or reopen growth following a close spike. The exact read-only queries, counter dictionary, invariant checks, and index verification are in the [A09 runbook section](./SOURCE_CONTROL_RUNBOOK.md#a09-link-check-index-and-observability). There is no A09 CMS threshold or moderation panel: the three-user/seven-day/24-hour report policy remains code-owned, while operations consume Inngest status, structured logs, `JobIngestCycle`, and read-only Mongo views.

Source-acquisition request budgets are Redis-atomic hard per-run/UTC-day/UTC-month caps over physical attempts, including retries. The next attempt at any exact cap is rejected and unavailable Redis fails closed. An 80% display/alert is advisory only; source cadence does **not** halve at 80%, and there is no 95% source-stop transition. The 80%/95% degradation policy in §4.5 belongs only to the separate LLM verdict budget breaker.

CMS dashboard `/cms/jobs-ingest` is the normal A08 operator surface: configuration/runtime status, explicit safe bootstrap state, per-source operational/legal state, credentials by status only, bounded cadence/request settings, 24h/7d yield and quality, budgets, cold validation, permanent command history, and explicit Enable/Pause/Run now/Validate/Revoke/Restore actions. Operational audit command fields are permanent, while dispatch and terminal outcome fields are one-way post-commit markers; the history is not accurately described as an immutable/append-only row collection. A queued Validate/Run-now response is not terminal: operators refresh and match its operation ID to succeeded/failed completion plus validation/cycle evidence.

Bootstrap creates only missing deploy-reviewed catalog rows, atomically establishes safe empty metadata, and leaves inserts paused; it never accepts an arbitrary adapter, URL, or credential name from CMS input. A safe enabled-but-unaudited legacy row is adopted through an audited Pause and then requires Validate → Enable. Unknown/routing-drift identities, existing data without protected lineage metadata, revoked epochs without legal evidence, and explicitly malformed/negative operational revisions block bootstrap for protected migration. Settings changes pause an active source, advance the independent operational revision, and invalidate older validation. Pause stops future source work without hiding existing postings. Revoke is the legal action that advances authority and restricts lineage. Restore remains clearance-only, followed by current-revision cold Validate and explicit Enable. Credential rotation is deployment configuration: Pause if active, rotate/redeploy, then revalidate; an old rejected result does not block a new check. Provider secrets are never readable or editable in CMS.

Mongo replica-set/sharded transactions and shared reachable `REDIS_URL` are mandatory. Inngest environment variables prove configuration only; deployed registration plus delivered terminal `jobs/source.validate` and `jobs/source.sync` canaries are separate launch gates. The provider-egress deployment smoke above must pass too. Raw command APIs are break-glass/automated-rollout surfaces, not routine workflow; never edit source rows or audit collections directly. Monday digest email; immediate alerts only for quarantine, source quota >80% (advisory), failStreak ≥2, storage >300 MB, **[AMENDED 2026-07-12]** verdict backlog age >48h, LLM budget >80%, disagreement-rate spike per source. Kill switch: DATA, not flags (founder correction 2026-07-13) — Pause sets `JobSourceConfig.enabled:false`; legal Revoke additionally sets `health:'revoked'` and closes the source corpus.
